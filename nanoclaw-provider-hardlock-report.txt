# NanoClaw Gateway Provider Hard-lock 修复与 live-audit 实测汇报

## 1. 问题背景

用户要求：通过项目入口让本地政策 Agent 实搜“找上海医疗最新补贴”，而不是绕过项目直接调用外部 Search MCP。

最初错误：我绕过了项目入口，直接用外部 search/fetch 工具查了上海医疗补贴。这不符合验证目标，因为无法证明本项目里的 Heavy Prompt、runPolicyTaskLoop、search/fetch runtime 是否真实有效。

随后改为从项目入口运行：

```bash
cd /Users/lingion/repo-downloads/local-policy-agent

LIVE_AUDIT_TOPIC='找上海医疗最新补贴' \
LIVE_AUDIT_MAX_ITERATIONS=4 \
LIVE_AUDIT_OUTPUT_DIR=/Users/lingion/repo-downloads/local-policy-agent/outputs/live-audit-shanghai-medical-subsidy \
POLICY_SEARCH_BACKEND=search-mcp \
pnpm live-audit
```

结果：Agent 尚未进入 runPolicyTaskLoop，就在 preflight 阶段失败。

关键错误：

```text
Live audit preflight failed before entering runPolicyTaskLoop:
Gateway returned verified empty response after retries
```

诊断输出显示：

```json
{
  "transport": "nanoclaw",
  "provider": "anthropic",
  "model": "gpt-5.4",
  "effectiveBaseURL": "https://987xyz.com/",
  "gateway": {
    "ok": true,
    "includesConfiguredModel": true,
    "configuredModel": "gpt-5.4"
  }
}
```

这说明 `/v1/models` 可用，模型存在，但 runtime 把 `https://987xyz.com/` 错误推断为 Anthropic provider，导致用 Anthropic `/messages` 协议打一个 OpenAI-compatible gateway，最终返回 200 但无可解析文本。

---

## 2. 根因结论

根因不是 Heavy Prompt，也不是 Search MCP，也不是 Agent 判断力。

根因是：

```text
src/runtime/nanoclaw-bridge.ts 的 provider 自动推断逻辑过于脆弱。
```

旧逻辑：

```ts
const provider =
  process.env.NANOCLAW_LLM_PROVIDER === 'openai' || process.env.NANOCLAW_LLM_PROVIDER === 'anthropic'
    ? process.env.NANOCLAW_LLM_PROVIDER
    : /\/chat\/completions$/i.test(baseURL) || /openai/i.test(baseURL)
      ? 'openai'
      : 'anthropic';
```

问题：

- `https://987xyz.com/` 本质上是 OpenAI-compatible gateway；
- 但 URL 不包含 `openai`，也不以 `/chat/completions` 结尾；
- 所以旧逻辑默认推断为 `anthropic`；
- provider 一错，endpoint / body / response parser 全错；
- preflight 直接在起飞前失败。

这是典型的“隐式 provider 推断”生产风险。

```ts
test('nanoclaw bridge hard-locks known OpenAI-compatible gateway hosts even when only ANTHROPIC_* env vars are set', () => {
  const original = {
    NANOCLAW_API_KEY: process.env.NANOCLAW_API_KEY,
    NANOCLAW_BASE_URL: process.env.NANOCLAW_BASE_URL,
    NANOCLAW_LLM_PROVIDER: process.env.NANOCLAW_LLM_PROVIDER,

  delete process.env.NANOCLAW_API_KEY;
  delete process.env.NANOCLAW_BASE_URL;
  delete process.env.NANOCLAW_LLM_PROVIDER;
```

### 4.2 实现修复

文件：

```text
src/runtime/nanoclaw-bridge.ts
```

新增 provider hard-lock 函数：

```ts
function inferProviderFromBaseUrl(baseURL: string): NanoclawRuntimeConfig['provider'] {
  try {
    const hostname = new URL(baseURL).hostname.toLowerCase();
    if (hostname === '987xyz.com' || hostname.endsWith('.987xyz.com')) {
      return 'openai';
    }
  } catch {
    // Fall through to path-based inference for malformed-but-usable gateway strings.
  }

  return /\/(chat\/completions)$/i.test(baseURL.replace(/\/+$/, '')) || /openai/i.test(baseURL)
    ? 'openai'
    : 'anthropic';
}
```

修改 `resolveNanoclawRuntimeConfig()`：

```ts
const provider =
  process.env.NANOCLAW_LLM_PROVIDER === 'openai' || process.env.NANOCLAW_LLM_PROVIDER === 'anthropic'
    ? process.env.NANOCLAW_LLM_PROVIDER
    : inferProviderFromBaseUrl(baseURL);
```

语义：

- 用户显式指定 provider 时，尊重用户；
- 未指定 provider 时，`987xyz.com` 强制识别为 `openai`；
- 其他未知 URL 继续走原路径推断逻辑。


```text

```

### 仍需注意

本次 `LIVE_AUDIT_MAX_ITERATIONS=2` 是短跑验证，所以最终被 gate 截断：

```text
loop_interrupted_by_gate: true
final_decision: continue_fetch
```

这不是失败，而是 max iterations 到达导致中断。若要生成完整 final_package，需要提高 `LIVE_AUDIT_MAX_ITERATIONS` 再跑完整流程。
